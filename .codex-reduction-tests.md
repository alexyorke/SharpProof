## Likely-unused/duplicate checks

- No unreferenced `SharpProof.Testing` type was found in the scoped search. Both core types have direct production/fuzz and test consumers.
- The generated specs witness is not unused: the generator, acceptance contract, and partial test class establish a deliberate source/generated split.
- Samples are intentionally tiny and are referenced by the sample solution/docs; their line count is not evidence of dead code.
- Architecture tests contain many repeated mutation names such as `duplicate`, but those are adversarial inputs, not duplicate implementation.
- Existing audit history classifies the scoped high-value files as retained regression or safety evidence rather than removable code (`docs/code-usefulness-audit.md:685-739`).

## Recommendation

Treat the first two rows as refactoring opportunities only, not safe LOC removals. The only defensible immediate reduction is housekeeping inside private test helpers after a baseline run and a full post-change run of the affected test project plus acceptance/generation checks. Do not remove smoke, generated, oracle, or individual adversarial regression cases based on apparent duplication.

## Validation plan for any approved refactor

1. Record clean-checkout baselines for `SharpProof.ArchitectureTest`, `SharpProof.Fuzz.Test`, `SharpProof.Effects.Test`, `SharpProof.Specs.Test`, and `SharpProof.Testing.Test` using the repository's container entrypoint.
2. Apply one candidate at a time; inspect generated-file and acceptance diffs.
3. Re-run the targeted project and then the relevant acceptance/generator gate.
4. Compare test counts, failure evidence, coverage identity, catalog digests, and generated-file determinism. A passing build alone is insufficient for these tests.
