### 296. [NOT REPRODUCED] Binding an Unconstructed Generic Method Definition Crashes ContractCanonicalization.CreateTypeSpecializer With a Raw IndexOutOfRangeException Instead of Any ContractBindingFailure

**Status**: The reported raw `IndexOutOfRangeException` was not reproducible with the current Roslyn symbols: generic definitions expose matching type-parameter/type-argument arity, and binding returns the typed `UnsupportedExpression` result. `UnconstructedGenericMethodDefinitionReturnsTypedFailure` records this guard. No production change is claimed for this report; retain it as a rejected lead unless a custom symbol provider reproduces the unchecked-arity shape.

**Location**: `SharpProof.Contracts\ContractCanonicalization.cs` (Lines 18-20 first `AddParameters` call; Lines 192-200 `AddParameters` indexing `arguments[index]`; same hazard repeated for the partial counterpart at Lines 43-45); reached eagerly from `SharpProof.Contracts\ContractBinder.cs` Line 112 (`_canonicalization.CreateTypeSpecializer(source)` evaluated before the `ContractExpressionBinder` constructor, with no catch on the path).
**Description**: `CreateTypeSpecializer` builds its substitution map with `AddParameters(source.OriginalDefinition.TypeParameters, source.TypeArguments)`. For an unconstructed generic method definition, `IMethodSymbol.TypeArguments` is EMPTY while `TypeParameters.Length >= 1`, so the loop executes `arguments[0]` on a zero-length ImmutableArray and throws raw `IndexOutOfRangeException`. Nothing in `ContractBinder.BindCore` catches it: the typed failure taxonomy (`UnsupportedExpression`, `CompanionSignatureMismatch`, ...) is bypassed entirely. Contrast the companion path, which carefully converts the analogous arity problem into a typed result (`ContractForSymbolMatcher.SpecializeCompanion`, Lines 269-284: `method.Construct(...)` wrapped in `catch (ArgumentException)` -> `CompanionSignatureMismatch`) - proving untyped crashes here are unintended. Reachability: (1) public API, certain - `ContractBinder.Bind/BindRequires/GetClauseInventory` accept arbitrary IMethodSymbols; passing the declared generic definition deterministically throws; no test pins definitional binding (every fixture resolves targets through invocation syntax, i.e., constructed symbols). (2) Shipped analyzer pipeline, conditional - `RequiresCallSiteAnalyzer.AnalyzeCallSite` binds `candidate.TargetMethod.ReducedFrom ?? candidate.TargetMethod` unconditionally (RequiresCallSiteAnalyzer.cs Lines 244-246, 265), and if Roslyn's ReducedFrom yields the unsubstituted declaration for constructed generic extension invocations every such callee hits the crash; no fixture defines a generic extension method, so the vector is unpinned. Distinct from #106 (NRE formatting a null extension-receiver type), #169 (SingleOrDefault crash for duplicate intrinsics), #275 (nullability-spelling rejection), #167/#274 (companion discovery/resolution): this is an eager arity-mismatch index fault in type-parameter specialization escaping the closed ContractBindingFailure contract.
**Reproduction Steps**:
1. Compile `public static class Target { public static T Read<T>(T value) { Contract.Requires(value != null); return value; } }` with `SHARPPROOF_CONTRACTS` defined.
2. Resolve `Read` as its definition symbol (e.g., `GetTypeByMetadataName("Target").GetMembers("Read")`) and call `new ContractBinder(compilation, new IrFactory()).Bind(definition)`.
3. Expected: a typed `ContractBindingFailure` (or success); actual: `IndexOutOfRangeException` thrown from `ContractCanonicalization.AddParameters` out of `Bind`.
**Confidence**: High (the indexing fault and its eager execution before any catch site are code-certain; only the second pipeline vector is conditional on Roslyn ReducedFrom semantics).

### 311. [DEFERRED API DESIGN] Evidence-Authority Validation Is Structurally Unreachable Through the Public ValidateForRequest API - External Embedders Silently Receive Strictly Weaker Tamper-Detection Than the Shipped Launcher

**Location**: `SharpProof.Worker.Protocol\ProtocolJson.cs` - public overload (hardwires no authority; ValidateResponse called without evidenceAuthority) vs internal overload requiring IWorkerResponseEvidenceAuthority; authority hook consumed only inside ValidateResponse when non-null; interface `ResponseEvidenceAuthority.cs` is internal.
**Description**: After the evidence-authority tier was added (the layer binding response rows to the compiler artifact, shown essential on the compact wire form by the #231 saga), the only signatures able to supply it are internal. The public `WorkerProtocolJson.ValidateForRequest(response, requestHash, inputHash, manifest, request, versions[, grace])` always validates with no authority, so the authority-derived checks are skipped entirely. Every non-launcher embedder of the documented public API silently receives strictly weaker validation with no compile-time signal, while the shipped launcher uses the internal overload. The result is a two-tier trust boundary inside one public type: identical inputs yield IsValid == true publicly and IsValid == false internally (e.g., a response whose assumption rows disagree with the artifact). Either the authority parameter belongs on the public surface or the asymmetry should be documented; today it is neither. Distinct from #231 (which documented the launcher passing the authority and the authority rejecting the compact marker, since fixed): this is the accessibility split itself, not a rejection bug; not #185 (a different assembly's validator).
**Reproduction Steps**:
1. From a test project referencing only public APIs, craft an otherwise-valid response whose effect-claim rows contradict the compiler artifact.
2. Call the public WorkerProtocolJson.ValidateForRequest(...) - result is valid; no public path can enable the authority machinery.
3. Run the launcher's internal-overload validation on the same input - authority-derived errors appear. Same assembly, same input, two verdicts.
**Confidence**: Medium (accessibility split and null-threading are verified facts; defect-vs-deliberate-internal-hardening inferred from the launcher being the sole entitled consumer).

**Status**: Deferred as an API/design decision. The documented public surface does not expose worker evidence-authority types, while the launcher is the sole current consumer of the internal authority overload. No public API was added solely for this audit; any future exposure requires an explicit compatibility and trust-model decision.
