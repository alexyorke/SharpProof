# Frontend reduction findings

Scope reviewed: `SharpProof.Frontend` and `SharpProof.Frontend.Test`. This is an analysis-only report; no production or test files were changed.

## High-confidence reductions

1. **Centralize duplicated Roslyn platform-reference fixtures.**
   - `SharpProof.Frontend.Test/FrontendLoweringTests.cs:1469`
   - `SharpProof.Frontend.Test/ProgramLoweringTests.cs:890`
   - `SharpProof.Frontend.Test/OpaqueSemanticIdentityTests.cs:200`
   - `SharpProof.Frontend.Test/UnaryAndDefaultLoweringCoverageTests.cs:367`
   - `SharpProof.Frontend.Test/ContractApiIdentityResolverTests.cs:309`
   Each file independently exposes/builds the same `ImmutableArray<MetadataReference>` from the runtime's trusted platform assemblies. Move this into one test-only fixture/helper (or a shared test utility project) and have the tests append custom references locally. This removes five copies of path/reflection logic and reduces the chance that one test fixture diverges.

2. **Share the repeated `CSharpCompilation` construction helper.**
   - `SharpProof.Frontend.Test/ReferencedTypeSymbolsTests.cs:159`
   - `SharpProof.Frontend.Test/CompilationModelProviderTests.cs:81`
   Both helpers construct a named `CSharpCompilation` from syntax trees with essentially the same defaults/references. A shared helper accepting name, trees, references, and optionally compilation options would make the intent explicit while preserving each test's custom inputs.

3. **Share repository-root discovery.**
   - `SharpProof.Frontend.Test/ContractApiCatalogTests.cs:55`
   - `SharpProof.Frontend.Test/ContractApiCatalogParityTests.cs:265`
   These are duplicate upward-directory searches for `SharpProof.sln`, including the same failure behavior. Keep one test utility and use it from both catalog test classes. This is a straightforward deletion of duplicated filesystem traversal code.

4. **Consolidate lowering-test source/operation plumbing.**
   - `SharpProof.Frontend.Test/FrontendLoweringTests.cs` contains a large `Compiled` fixture and several local lowering/reference helpers (notably around `1278`, `1454`).
   - `SharpProof.Frontend.Test/ProgramLoweringTests.cs:834` and `UnaryAndDefaultLoweringCoverageTests.cs:287` each implement another source-to-compilation-to-lowering pipeline.
   The suites repeatedly create parse options, compilations, semantic models, operation extraction, and lowerers. A shared `FrontendTestCompilation`/`LowerExpression` helper with narrow options would remove ceremony from dozens of cases. Preserve specialized helpers where they encode a distinct assertion (program CFG lowering vs expression lowering).

## Medium-confidence simplifications

5. **Remove the duplicate invalid-enum check in the operation-support path, or make ownership explicit.**
   - `SharpProof.Frontend/OperationSubsetClassifier.cs:16-26` validates `OperationKind` with `Enum.IsDefined` and then calls `OperationSupportCatalog.IsSupported`.
   - `SharpProof.Frontend/OperationSupportCatalog.cs:15-21` repeats the same validation.
   The public classifier already handles invalid values and is the normal production caller (`rg` found the other call only in a parity test). The catalog can be a pure projection lookup, or the classifier can delegate invalid handling to it; retaining both checks is defensive but redundant. Do not change this without checking whether future internal callers are intended to pass arbitrary enum values.

6. **Replace linear catalog scans with generated name maps only if profiling justifies it.**
   - `SharpProof.Frontend/ContractApiMetadataRuntime.cs:15-52` linearly scans `Methods` and `Attributes` for every lookup, while `IsContractMethodCandidateName` already uses a set.
   This is a potential shorter/faster generated representation (dictionary or immutable lookup), but it is not a clear code-size win unless the generated catalog grows. Treat as an optimization, not a priority reduction.

## No safe dead-code deletion identified

- The generated projection files are referenced (`CompilerIdentityProjections` from `CompilerIdentityBridge`; `OperationSupportProjections` from `OperationSupportCatalog`) and carry generator ownership comments.
- `ContractApiMetadataRuntime` members are partial-runtime implementations consumed by the resolver/catalog surface even where direct textual calls are indirect through the partial class.
- The apparent repetition in `RoslynOperationLowerer` and `RoslynProgramLowerer` is mostly semantic branching for distinct Roslyn operation kinds and abstention rules; collapsing it risks changing lowering behavior.

## Suggested order

1. Shared test utility for platform references and repository root.
2. Shared compilation/lowering fixture, incrementally migrating suites.
3. Revisit the enum-validation duplication after confirming the intended internal API boundary.
