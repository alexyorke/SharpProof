# Worker-scope complexity and unused-code review

Scope reviewed: `SharpProof.Worker`, `SharpProof.Worker.Protocol`, `SharpProof.Worker.Launcher`, `SharpProof.Host`, and `SharpProof.Worker.Test`. This is a static review; no source files were changed. Generated files and package-lock files are called out but are not recommended manual edit targets.

## Highest-confidence reduction candidates

1. **Split the launcher orchestration from argument parsing and publication.** `SharpProof.Worker.Launcher/Program.cs` is 1,038 lines and contains process execution, failure classification, validation/reporting, publication transaction/rollback, argument parsing, presentation, and generated partial members. The dense spans are `RunMain`/`RunWorker` (roughly lines 18-255), publication (508-803), and `LauncherArguments` (827-1033). These responsibilities have separate invariants and already have distinct test clusters (`WorkerProgramTests`, `LinuxPublicationSetTests`, `ContainerContractTests`). Moving each into a small internal service would reduce branching and make dead paths easier to identify. Confidence: high. Risk: preserve exact exit codes and atomic rollback semantics.

2. **Remove or justify duplicate request-construction overloads.** `LauncherArguments` exposes `CreateRequest` twice at lines 879 and 885. Compare their call sites before deleting one; if both are needed, rename them to encode the meaningful distinction. Overloads with near-identical signatures make it harder to determine which preflight/defaulting path is authoritative. Confidence: medium pending call-site inspection.

3. **Centralize launcher path/limit policy.** `Program.cs` has separate helpers for `ResolveDotNetHostPath`, `ValidateDotNetHostPath`, `NormalizeAbsolutePath`, `ComputeHardLimit`, `ComputeFinalLimit`, and two `ComputeExpectedInputHash` overloads (lines 257-347). These are policy calculations mixed into the top-level orchestration. A single immutable preflight result would reduce repeated normalization and make the invariant “validated path and computed limits travel together” explicit. Confidence: high.

4. **Treat `LinuxPathIdentity.cs` as a separate subsystem.** `SharpProof.Host/LinuxPathIdentity.cs` is 954 lines, including native ABI structs, locking, publication identity, and filesystem validation. The large file is not necessarily unused, but it is a strong complexity boundary: isolate native interop/ABI declarations from publication identity and lock orchestration. The ABI fields around lines 900-923 should remain exact and should not be simplified mechanically. Confidence: high for decomposition, low for deletion.

5. **Reduce protocol hand-written plumbing only after schema/codegen audit.** `ProtocolJson.cs` is 1,077 lines, `ProtocolJsonSupport.cs` 320, and generated protocol model code 1,001 lines. The project also contains `ProtocolModel.schema.json` and `ProtocolModel.generated.cs`. First establish which serializers/validators are schema-generated versus required compatibility code. Candidate simplification is consolidating repeated validation/error accumulation helpers, not deleting generated members. Confidence: medium.

## Likely simplifications, not proven unused

- `SharpProof.Worker/SharpProofWorker.cs` (633 lines) combines backend ownership, verifier construction, request execution, and disposal. The nested state around lines 547-551 duplicates mutable ownership state (`_backendFactory`, `_ownedBackend`, `Backend`, `Verifier`, and `ReadConsumedResourceCount`). A single context/state object could reduce lifecycle complexity. Confidence: medium.
- `SharpProof.Worker/VerificationCache.cs` has internal test hooks at lines 21-22 (`PathValidationOverride`, `TransactionRollbackOverride`). They appear intentionally injectable for failure-path tests; do not remove without confirming all test references. Confidence: low for unused, medium for encapsulation.
- `SharpProof.Worker.Protocol/BoundedReadStream.cs` is a focused 182-line utility and should not be folded into the large JSON implementation unless call-site evidence shows it is one-use glue. Confidence: low reduction value.
- `SharpProof.Host/LinuxWorkerProcess.cs` is 268 lines and has a clean process-lifecycle boundary. Constants and native methods are used by the lifecycle code; no safe deletion was established by static search. Confidence: low for unused code.

## Test-suite complexity

`SharpProof.Worker.Test/WorkerTests.cs` is 7,398 lines; `CompilerManifestArtifactTests.cs` 2,840; `ClaimManifestBuilderTests.cs` 2,584; and `ProtocolJsonTests.cs` 2,594. These are likely multiple suites accumulated in single files rather than unused code. Split by behavior/fixture (protocol limits, malformed input, publication, compiler artifacts, claim projection) to improve discoverability and reduce fixture setup duplication. Preserve the existing test names initially, then deduplicate helpers with coverage checks. Confidence: high.

The test project contains many narrowly named regression files plus broad mega-files. A useful first pass is to measure duplicate setup/assertion helpers and test method counts before moving code; avoid deleting tests based only on low apparent uniqueness because several files encode security and compatibility invariants.

## No deletion established

Static scans found no safe, evidence-backed unused production type or constant. Native constants in `LinuxPathIdentity.cs`, process signals in `LinuxWorkerProcess.cs`, protocol limits in `ProtocolJson.cs`, and generated model members should be presumed live until compiler/reference analysis confirms otherwise. `LauncherMarker` and generated partials likewise need project/build inspection before removal.

## Validation

Repository inventory and bounded symbol searches were run over the requested directories. A full build/test was not run in this review, so compiler warnings, linker trimming, and runtime-only reflection usage remain open evidence gaps. Recommended next gate: build the worker, protocol, launcher, host, and worker-test projects with warnings enabled; then run the targeted tests covering launcher arguments, worker program behavior, protocol JSON/schema, and publication rollback.
