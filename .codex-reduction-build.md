# SharpProof build and packaging reduction analysis

Scope: static review of `SharpProof.Package`, `SharpProof.BuildTasks`, `SharpProof.CompilerArtifact`, `SharpProof.CompilerCollector`, `SharpProof.CompilerProbe.TestAsset`, solution/build scripts, and packaging code. Line references are 1-based. Confidence describes confidence that the item is a genuine simplification opportunity, not that the current code is incorrect.

No source code was modified. The existing dirty-worktree changes were preserved, and `reductions.md` was not modified.

## Findings

### 1. Consolidate package metadata sources

- Files: `SharpProof.Package/SharpProof.Package.csproj:14-20`; `SharpProof.Package/SharpProof.nuspec:4-15`; `SharpProof.PackageMetadata.props:3-14`; `SharpProof.Release.props:3-14`. The same package description, release notes, copyright, tags, authorship, license, project URL, repository, and readme information is split between project metadata, shared props, release props, and the nuspec.
- The same pattern is repeated for the verifier in `SharpProof.Verifier/SharpProof.Verifier.csproj:14-20` and `SharpProof.Verifier/SharpProof.Verifier.nuspec:4-19`.
- Rationale: choose one authoritative metadata source (shared props plus generated nuspec properties, or project metadata plus a payload-only nuspec). Keep explicit file lists separate if they are needed, but remove duplicated descriptive metadata. This reduces release drift and makes a metadata change one edit.
- Confidence: High. The file payload behavior should be regression-tested before removing any nuspec fields.

### 2. Generate the package dependency/file inventory once

- Files: `SharpProof.Package/SharpProof.nuspec:28-66`; `SharpProof.Package/buildTransitive/SharpProof.targets:21-63`; `SharpProof.AnalyzerConsumer.props:33-72`.
- The analyzer, collector, shared library, and BCL/System dependency names are manually repeated in the nuspec file list, in two installed-package MSBuild `Analyzer` item groups, and in the source-tree consumer props. The installed target groups currently cover the same package payload roles as the nuspec, but each list can drift independently.
- Rationale: define a small inventory with role (`Portable` or `Collector`), assembly name, package target path, and source-tree path, then generate or consume it from the nuspec and both MSBuild paths. This is especially worthwhile because `LauncherRuntimeCompanionInventory.generated.cs` and `SharpProof.Worker.Launcher/LauncherArguments.catalog.json` already establish an inventory/catalog pattern in the repository.
- Confidence: High. Preserve the current analyzer ordering and package target paths in package-consumer tests.

### 3. Remove duplicate path computation between package props and targets

- Files: `SharpProof.Package/buildTransitive/SharpProof.props:3-12`; `SharpProof.Package/buildTransitive/SharpProof.targets:3-11`.
- The props file computes `_SharpProofAnalyzerDirectory`, `_SharpProofAnalyzerPath`, and `_SharpProofCollectorDirectory`; the targets file recomputes/normalizes those paths and also computes `_SharpProofSharedDirectory` and the collector path. The props-time private paths are not needed by the `CompilerVisibleProperty` declarations.
- Rationale: keep only consumer-overridable defaults and the `_SharpProofContractForGeneratorPathWasDefault` marker in props; calculate private absolute paths once in targets. This removes import-time work and makes path ownership clearer. Preserve the marker because targets use it to distinguish the default generator contract from an explicit override.
- Confidence: High. Verify unusual import-order consumers and the package acceptance tests after the change.

### 4. Share the common package/source-tree MSBuild configuration

- Files: `SharpProof.Package/buildTransitive/SharpProof.targets:12-93`; `SharpProof.AnalyzerConsumer.props:5-135`.
- Both files define defaults for profile/features/verification, analyzer and dependency groups, validation of configuration values, and source/package dependency wiring. Their main differences are the source-tree versus installed-package roots and the source-tree verifier guard; the source-tree file also has broader `CompilerVisibleProperty` declarations.
- Rationale: extract shared item/property fragments or generate role/path items from one definition. Leave only the environment-specific roots and the genuinely different guards in each file. This reduces parallel edits when a dependency, feature, or configuration property changes.
- Confidence: High. Treat the source-tree consumer as a compatibility surface and retain its distinct override behavior.

### 5. Eliminate the second replay-geometry validation pass

- Files: `SharpProof.CompilerArtifact/CompilerManifestArtifact.cs:891-933`; `SharpProof.CompilerArtifact/CompilerEffectClaimArtifactCodec.cs:42-98`.
- `CompilerManifestArtifact` first calls `CompilerEffectClaimArtifactCodec.HasValidReplayGeometry(effectClaim, compilation)`, then loops over every replay event and repeats the null, ordinal-range, tree, tree-hash, snapshot-hash, start, and length checks. The codec helper already performs those per-event checks, plus line-map/source-tree binding checks.
- Rationale: make the codec helper the single authoritative geometry validator, or factor a common event predicate if a second validation boundary is required. The current second loop adds maintenance cost without a distinct predicate.
- Confidence: High. Confirm that callers do not depend on a particular exception/diagnostic ordering before changing the boundary.

### 6. Reuse source-location and witness comparison helpers

- Files: `SharpProof.CompilerArtifact/CompilerSourceLocationAuthority.cs:224-247`; `SharpProof.CompilerArtifact/CompilerEffectAuthority.cs:206-213,285-296`; `SharpProof.CompilerArtifact/CompilerResponseEvidenceAuthority.cs:923-949`.
- `CompilerSourceLocationAuthority` already provides `CopyLocation` and `LocationsEqual`, while `CompilerEffectAuthority` privately reimplements both. Response evidence also has a private location comparison and a witness comparison that duplicates the effect witness fields (`Kind`, `Detail`, effects/capabilities, exception array, and location).
- Rationale: use the shared source-location helpers and introduce one internal witness comparer/authority helper for the common witness shape. Keep any policy-specific comparison in the owning authority, but centralize mechanical field equality and copying to prevent semantic drift.
- Confidence: High for locations; Medium-high for witness equality because nullability and authority-boundary semantics need focused tests.

### 7. Simplify manifest validation and deserialization staging

- Files: `SharpProof.CompilerArtifact/CompilerManifestArtifact.cs:302-369,403-437,689-755`.
- `Serialize` validates diagnostic shapes, canonicalizes values, then calls `Validate`, which reaches `HasValidDiagnostics`; `HasValidDiagnostics` checks diagnostic shapes again. `Deserialize` parses the raw JSON once for specification-pack authority properties and again for diagnostic classification properties, then validates and calls `Serialize`, causing another validation and canonical serialization pass.
- Rationale: use one parsed `JsonDocument` for the raw-envelope checks and split canonical serialization from public validation, or return a validation result that records the shape checks already completed. Retain the explicit canonical/authentication checks; the opportunity is to avoid repeated traversal and parsing, not to remove validation.
- Confidence: Medium-high. Serialization is security-sensitive, so preserve canonical bytes and rejection behavior with focused artifact tests.

### 8. Remove the unused `interrupted` parameter from supervisor deferral

- Files: `SharpProof.BuildTasks/RunVerifier.cs:306-311,494-501`.
- `ShouldDeferSupervisorAuthentication` accepts `interrupted`, immediately discards it with `_ = interrupted`, and returns only `authenticationRequired && !outputCompleted`. The caller passes the value, but it has no behavioral effect.
- Rationale: remove the parameter and the dead local/call plumbing, then update the focused BuildTasks tests. This makes the actual deferral contract explicit.
- Confidence: High.

### 9. Centralize common POSIX interop declarations in BuildTasks

- Files: `SharpProof.BuildTasks/RunVerifier.cs:1321-1345`; `SharpProof.BuildTasks/VerifierProcessSupervisor.cs:407-444`.
- Both `NativeMethods` types declare the same libc `close`, `syscall` (two- and four-argument forms), and related calling/signature metadata. The supervisor type additionally owns `prctl` and `waitpid`.
- Rationale: move only the common declarations to one internal `PosixNativeMethods` type and retain process-supervision-specific declarations separately. This removes signature duplication while keeping the security-sensitive APIs isolated and reviewable.
- Confidence: Medium-high. Preserve exact entry points, `SetLastError`, argument types, and platform guards; run the Linux container tests because a mechanical interop refactor has a high blast radius.

### 10. Factor the repeated BuildTasks polling/deadline primitive

- Files: `SharpProof.BuildTasks/RunVerifier.cs:396-479,817-837`.
- `WaitForOutputCompletion`, `WaitForSupervisorReadiness`, and `WaitForExitOrCancellation` each implement a stopwatch/deadline loop with short waits, cancellation handling, and timeout behavior. Their completion predicates and timeout results differ.
- Rationale: extract a small internal deadline/poll helper that owns the timing and slice calculation while accepting the distinct completion predicate and cancellation/timeout action. Do not merge the state machines or alter their result semantics.
- Confidence: Medium. This is useful only if the helper remains small; preserve test overrides and diagnostics exactly.

### 11. Share BuildTasks path and optional-value utilities

- Files: `SharpProof.BuildTasks/InvalidatePublishedResult.cs:77-90,258-260`; `SharpProof.BuildTasks/ResetPublishedVerification.cs:23-35,51-54`; `SharpProof.BuildTasks/ValidatePublishedVerificationResult.cs:27-39`.
- The three tasks repeat the same project-directory fallback and local-path resolution setup. `InvalidatePublishedResult` and `ResetPublishedVerification` also repeat the same `Present(params string?[])` helper.
- Rationale: introduce an internal `BuildTaskPathResolver` for the project-rooted lexical resolver/local path boundary and a shared optional-value formatter. Keep the existing rooted/relative path validation and error messages as the security contract.
- Confidence: Medium-high. Verify task diagnostics and path traversal tests because these helpers sit on an input-validation boundary.

### 12. Consolidate duplicate compiler-probe option/path helpers

- Files: `SharpProof.CompilerProbe.TestAsset/CompilerProbeGenerator.cs:114-124`; `SharpProof.CompilerProbe.TestAsset/CompilerProbeSnapshot.cs:584-605`.
- Both files implement the same `GetOption` and `NormalizePath` logic in the same test-asset assembly.
- Rationale: move the helpers to one internal `CompilerProbe` utility and keep generator/snapshot-specific parsing in their owning classes. This removes a test-asset-only source of behavioral drift with minimal coupling.
- Confidence: High.

### 13. Factor repeated effect-claim binding in the collector producer

- File: `SharpProof.CompilerCollector/CompilerArtifact/CompilerManifestArtifactProducer.cs:31-66`.
- The diagnostics and normal-callable branches both map `EffectClaims` and `EffectAuthorities` through `CompilerEffectAuthority.BindSourceTree`; the branch-specific difference is the lowered-callable source.
- Rationale: bind effects once after selecting the lowered callable/diagnostic source, or use a local helper that maps claims and authorities. This shortens the producer and makes it harder for the two output modes to diverge.
- Confidence: High. Preserve the current branch-specific absence/presence behavior and authority ordering.

### 14. Factor package product build argument construction in PowerShell scripts

- Files: `scripts/Get-SharpProofDevCheckPlan.ps1:39-50`; `scripts/Invoke-SharpProofDevCheck.ps1:63-80`; `scripts/Invoke-SharpProofPackageTests.ps1:339-352`; `scripts/Invoke-SharpProofContainer.ps1:577-593`.
- The dev-check plan constructs the Release package-product build command, while the dev-check executor and package tests reconstruct equivalent arguments. The container dispatcher separately reads the package project manifest, builds the solution, and loops over package projects to pack them.
- Rationale: make the plan or a shared PowerShell function the single source for package-product build/pack arguments, and have all callers consume it. Preserve the intentional distinction between a full solution build and a Release package-product build; the simplification is orchestration, not removal of that distinction.
- Confidence: Medium-high. Keep the JSON plan schema stable if external tooling consumes it.

### 15. Derive package project/ID expectations from the package manifest

- Files: `scripts/package-projects.json:3-7`; `eng/acceptance/Verify.ps1:555-569`; `scripts/Test-SharpProofPackageConsumers.ps1:91-123`; `scripts/Get-SharpProofDevCheckPlan.ps1:18-19`; `scripts/Test-SharpProofContainerContract.ps1:419-432`.
- The same three package projects/IDs are hardcoded in release acceptance, package-consumer tests, and plan validation. The container contract additionally assumes that the verifier is the last package entry.
- Rationale: load project paths and IDs from `scripts/package-projects.json` everywhere, then assert only the policy that must remain fixed (for example, required package IDs and any verifier-last ordering requirement). This keeps release topology in one manifest while retaining explicit contract checks.
- Confidence: High for eliminating repeated lists; Medium for changing verifier ordering because that may be an intentional contract.

### 16. Reuse the repeated container test execution setup

- File: `scripts/Invoke-SharpProofContainer.ps1:231-271,321-342`.
- The direct project test and worker-tests branches each restore/build a project, locate the test assembly, and invoke `vstest`; only the project path and surrounding mode differ. The portable-tests branch has a related but intentionally different `dotnet test` path.
- Rationale: extract an `Invoke-SharpProofVstestProject` helper for the shared restore/build/assembly-discovery/vstest sequence, leaving portable-tests on its separate command path.
- Confidence: Medium-high. Preserve environment variables, test filters, result paths, and failure propagation.

### 17. Share hash-to-hex formatting within compiler capture

- File: `SharpProof.CompilerCollector/CompilerArtifact/CompilerCompilationCapture.cs:467-487`.
- The stream and byte-array hashing paths each create SHA-256 output and format the digest as lowercase hexadecimal separately.
- Rationale: use one local/internal digest formatter after the two input forms produce bytes. This is a small cleanup that reduces formatting drift without coupling the standalone probe asset's `ProbeHash` implementation to production code.
- Confidence: Medium. Low priority; take only if the surrounding hashing code is already being changed.

## Suggested order

1. Generate the package dependency inventory and consolidate package/source-tree MSBuild configuration.
2. Consolidate package metadata and package project/ID manifest usage.
3. Remove the redundant manifest replay pass and share location/witness helpers.
4. Apply the mechanical BuildTasks and probe helper cleanups.
5. Factor PowerShell orchestration only after package acceptance tests establish the current command-line contract.

## Validation notes

These are reduction opportunities, not implemented changes. For any implementation, run the repository-prescribed Linux amd64 container checks, with package-consumer/acceptance tests first for packaging changes and focused BuildTasks/compiler artifact tests first for runtime changes. Process supervision, path validation, canonical serialization, and authentication checks should remain explicit even when their mechanical helpers are shared.
