# Reduction audit: Verify, Verifier, Verify.Test, Gates, and Specs

Scope reviewed: `SharpProof.Verify`, `SharpProof.Verifier`, `SharpProof.Verify.Test`, `SharpProof.Gates`, and `SharpProof.Specs` (including tests and the verifier MSBuild integration). This is a static audit; no production code was changed and `reductions.md` was not modified.

## Findings

### No safe dead-path deletion identified

The apparent branches in `ProofKernel.VerifyAsync` are all externally meaningful:

- cancellation is checked before and after the backend call and before replay/evaluation;
- backend exceptions are converted to `InfrastructureFailure`, while cancellation and process-fatal exceptions are deliberately excluded;
- null results and unknown enum values are rejected as malformed;
- satisfiable results are replayed against every assumption and the goal, so the replay path is part of the soundness boundary;
- `CreateProven` and `ReplayCounterexample` reject inconsistent combinations of status, model, core, and failure reason.

The `BackendCheckResult` factory methods and `VerificationQuery` validation are used as the construction boundary for the generated model types. Their validation is not redundant with replay validation: the former protects callers/backends, while the latter protects the proof result.

The `SharpProof.Verifier` targets contain multiple conditions that look repetitive, but they distinguish design-time builds, unsupported hosts, disabled profiles, non-building invocations, package-owned paths, and per-target-framework files. Removing or merging them would change supported MSBuild scenarios. The invocation-id/path checks are security and cleanup guards, not dead code.

The gate command branches in `SharpProof.Gates.Program` are all represented by the documented command surface (`all`, corpus commands, performance commands). The source-bound standalone envelope is conditional by design: interactive runs may omit certification metadata, whereas certified builds must include it.

## Low-risk simplifications (style/size only)

These do not remove behavior and should be treated as optional reductions rather than correctness fixes:

1. `OutcomeCachePolicy.IsCacheable` can use an ordinary null guard followed by the type pattern instead of the conditional expression. This improves readability but does not reduce meaningful code or branches.
2. `ProofKernel.IsBoolean` can be expressed as a single pattern with the expected value, or inlined at its two call sites. Keeping the helper currently makes the replay invariant explicit, so inlining is not clearly better.
3. `Program.Main`'s command dispatch could be rewritten as a switch expression/statement, but the current explicit branches mirror the CLI documentation and are easier to audit for distinct exit codes.

## Spec and test observations

`SharpProof.Specs` has generated catalogs/models plus validation, instantiation, digest, and identifier code. The generated files are consumed by the tests and runtime-facing projects; they must not be treated as dead merely because their contents are generated. The large runtime-oracle tests intentionally contain exhaustive fallback/throw branches for detecting new enum/spec cases.

`SharpProof.Verify.Test/ProofKernelTests.cs` exercises proven, refuted, unknown, malformed, model-variable, replay, and cancellation behavior. The apparent helper fixture and repeated factory setup support independent tests and are not dead paths. No test was found that could be removed without reducing coverage of a distinct outcome or validation contract.

## Recommendation

Record this area as **no high-confidence reduction**. If a mechanical cleanup is desired, prefer only the three readability refactors above, one at a time, followed by the targeted Verify and Gates/Specs test projects. Do not delete validation branches, generated spec files, verifier target conditions, or exhaustive test fallbacks based on static reachability alone.
