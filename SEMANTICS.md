# SharpProof semantics

This document defines how to interpret the current verifier's results. The implementation authorities are the typed IR, compiler artifact, worker protocol validators, native VC checks, and replay code. The portable analyzer provides a separate, conservative analysis surface.

## Outcomes and evidence

| Claim outcome | Meaning |
| --- | --- |
| `Proven` | The modeled obligation holds under its recorded assumptions and entry domain |
| `Refuted` | A violating execution or effect site has been validated by concrete replay |
| `Unknown` | The claim could not be established or refuted within the supported model and limits |

An SMT satisfiable result alone is not a refutation. A solver failure, unsupported operation, invalid result, or failed replay cannot be promoted to success. Proofs are about the modeled executions and claim, not arbitrary program behavior.

Worker run status, callable coverage, and claim outcome are distinct. A complete run may contain Unknown claims. Every selected callable and claim must be accounted for by the manifest and response; missing results are protocol failures. Diagnostic silence, suppression, and a successful ordinary C# build are not proof evidence.

## Contracts and trust

Direct `Requires`, `Ensures`, and `Assume` calls form a contiguous prologue. They are compiler-bound to the verified Attributes API. A source lookalike or an unverified assembly contributes no contract evidence.

`Requires` restricts a callee's entry domain and creates obligations at modeled calls only; [Calls and loops](#calls-and-loops) lists the calls that stay unchecked. `Ensures` applies on normal return. `Result<T>` names that return value and `Old<T>` names entry state. `Assume` adds explicit user evidence; it is not independently proven.

Direct and companion clauses are alternative effective sources. Valid direct clauses take precedence for the member; a valid companion supplies clauses when there are no valid direct clauses. Invalid or misplaced clauses remain usage errors. Compiler-elided clause invocations, including their argument evaluation, are omitted from executable body semantics.

The `SHARPPROOF_CONTRACTS` symbol is unsupported. SharpProof supplies no runtime enforcement. See [public API](docs/public-api.md) for exact attribute and intrinsic rules.

Closed parameter and return attributes supply validated non-null, positive, or inclusive-range conditions. Invalid targets, unsupported types, and invalid values do not create facts.

Trusted boundaries and resolved API specifications are assumptions with provenance. `SharpProofTrusted` alone does not invent a complete effect summary. External complete effect declarations require the reviewed precondition-free certification accepted by the metadata reader. Reporting suppression changes no evidence. Assumption policy governs declared user assumptions and trusted boundaries; it does not reject every recorded precondition or API specification.

## Entry feasibility and vacuity

The worker checks entry feasibility separately from a body claim. Contradictory preconditions are recorded as vacuous entry evidence. Body facts, arbitrary user assumptions, and API results must not be reported as contradictory preconditions. Proofs that depend on user assumptions remain conditional on that declared evidence.

Postconditions constrain normal returns. A body with no modeled normal return may satisfy a postcondition vacuously; the response records `NoModeledNormalReturn`. This does not establish termination or exception freedom. Effect claims have their own obligations.

Input domains include modeled CLR constraints. An instance receiver is non-null. Closed sealed reference roots of incompatible runtime types cannot denote the same non-null object. Nullable inputs and compatible aliases remain possible.

## Typed execution model

Roslyn operations and CFG are lowered to typed Total IR. Integral operations carry their exact admitted width, signedness, conversion behavior, and checked/unchecked semantics. Normal and exceptional paths remain distinct. Unsupported numeric and expression forms abstain rather than borrowing an unrelated representation.

Built-in C# integer shifts (`<<`, `>>`, `>>>` and their compound forms) follow the CLR: the int count uses only its low five (32-bit) or six (64-bit) bits, `>>` is arithmetic for signed values, `>>>` is logical, and narrow operands are promoted to int. A C# compound shift on narrow storage narrows the result under the enclosing checked context. VB compound shifts on 8-bit or 16-bit storage instead mask the count by 7 or 15 and wrap the storage result regardless of overflow checking. See [compiled VB and C# controls](src/SharpProof.Frontend.Tests/VisualBasicNarrowCompoundShiftTests.cs). Admitted metadata IL shifts preserve stack width and distinguish arithmetic `shr` from logical `shr.un`; lifted and user-defined shifts abstain. See [metadata shift tests](src/SharpProof.Worker.Tests/MetadataIlShiftSemanticsTests.cs).

Built-in integer `&`, `|`, `^` and `~` (and their compound forms) apply to operands after C# numeric promotion, so narrow operands become int and mixed signed/unsigned operands take the common promoted type; they never overflow. Bool `&`, `|` and `^` evaluate both operands and are logical and, or and inequality. IL `and`, `or`, `xor` and `not` use the same operators. An enum value is its underlying integer: enum `&`, `|`, `^`, `~`, the six comparisons and `&=`, `|=`, `^=` act on that integer. A conversion to or from an enum converts the underlying integers and, in a checked context, faults like them (Roslyn marks only numeric conversions as checked, so the lexical context decides). Enum `+`, `-`, increments and other compound forms, and boxing an enum (a boxed enum is not a boxed integer) abstain. Lifted and user-defined bitwise operators abstain.

`float`, `double` and `decimal` values are opaque. They can flow through locals, parameters, returns and admitted calls. A built-in numeric conversion from an integer or `char` into these types, or from `float` to `double`, evaluates its operand and produces an unknown value without introducing an exception. A store to an admitted class field of these types checks the receiver and records the write. Built-in `float` and `double` equality and inequality yield unknown Boolean values. Arithmetic, ordered comparisons, conversions out of floating point and floating values in contract clauses remain unsupported.

Passive scalar SSA constraints preserve instruction ownership, predecessor edge guards, and source locations. Branch conditions restrict the corresponding paths. Multiple returns and exceptional exits are joined under their reach conditions.

Heap reasoning tracks modeled entry contents and ordered stores under path reach. A store of a scalar, or of a modeled struct value (below), into an element of a one-dimensional array is a store into that array; an array of structs aliases no array of another element type. Reads of struct elements stay approximations. Any other store into an element of a one-dimensional array, such as a reference stored into a `string[]` or a `T[]`, forgets memory, since arrays of different element types can be one object, but it still names the array. Either way replay tells a store into an array the body allocated, which no caller can see, from a store into one the caller can. A claimed method's own `ref` or `out` parameter of a scalar, reference or type-parameter type is its caller's storage, which may be a field, an array element or the same variable as another such parameter. A store to it is a write to argument state: it forgets memory and the other by-reference parameters, and the parameter keeps the stored value until the next write of any kind. A `ref` parameter starts with the caller's value; C# never reads an `out` parameter before the body assigns it. A constructor's stores to its own readonly instance fields and get-only auto-properties, through `this`, are modeled stores; C# allows no other store to them. A constructor of a modeled mutable struct (below) stores any of its own fields and auto-properties through `this` the same way. Instance field and property initializers store into the new object before anything can see it, since they cannot read `this`, so those stores are not effects either. A constructor declared `: this(arguments)` evaluates its arguments, then runs the other constructor on the same object, including that constructor's initializers, then its own body; its own type's initializers do not run again. `: this()` on a struct without a declared parameterless constructor only zeroes the value. A class whose base classes down to object are all declared in source, as ordinary classes without a destructor or a primary constructor, runs `: base(arguments)`, written or implicit, in C#'s order: its own initializers, then the arguments, then the base class's initializers, its own base constructor and its body, then its body. An implicitly declared constructor runs the base class's one parameterless constructor. Every field of such an object starts zeroed. The object's runtime type may be more derived than a base constructor's class, so a base constructor that calls a virtual member of `this`, other than through `base.`, is not modeled; nor is a base class declared in metadata other than object. A source struct that is not generic, record or ref-like, whose instance fields are scalars, references or other such structs, and which, unless it is `readonly`, has no primary constructor, is modeled as a reference to an immutable object, and `null` stands for `default(S)`. Every read of one of its fields is guarded: for `null` it yields the field's default, and it never faults. Its constructors, including a target-typed `new(...)` and chained ones, members and user-defined operators are inlined like those of a class. No modeled operation can tell a `null` from an object whose fields are all defaults, or two equal values from one: boxing yields an unconstrained reference, and C# has no reference comparison of struct values. The model builds such a value with an allocation the CLR does not make, so a body that constructs one is treated like an entry that constructs fresh values: purity and capability claims accept it, and allocation, effect-contract and resource-bound claims stay `Unknown`. C# passes a struct variable to its instance member by reference, so the callee's `this` is read from a local or parameter once the arguments have run. A struct that is not `readonly` keeps this model with C#'s copy semantics. A store into a field or a compiler-implemented auto-property of a local or by-value parameter, `+=` and `++` included, builds a new object holding the variable's fields as they are once the right-hand side has run, with that field replaced, and assigns it to the variable; a copy, element or box made earlier keeps the old object. A member that is not `readonly`, called on such a variable, runs on its own copy of `this`, and on normal return the caller assigns the callee's final `this` to the variable. Such a call is modeled only outside every try region, as a ref argument is, and only when its body is expanded; an unknown call of a member that may change the place it is called on, including an interface member or an override of an `object` member, is not modeled. Called on a value C# copies first (the result of a call, a property or `new`, a `foreach` or `using` variable, or `this` of a `readonly` member) the member changes only that copy. A mutation through any other place, such as a field of an object, an array element, a `ref` local, a struct field of a struct variable or an assignment to `this`, is not modeled. `this` of the claimed member itself, other than a constructor, is its caller's storage, which may be a field or an element: a store into it or a mutating call on it is not modeled, and its value is forgotten after any write to memory other than a store into an object the body built. Generic structs stay opaque values. `Nullable<T>` over a scalar (a `bool`, an integer or an enum) or over such a struct is modeled the same way: a `T?` value is a reference to an immutable object that holds the value, and `null` is "no value". `HasValue`, `GetValueOrDefault`, null tests, `??`, lifted equality and comparisons, lifted integer arithmetic, shifts and unary operators, `++`, `--` and compound assignment on a local or parameter, integer conversions between nullable and non-nullable types, and constant, relational, type and declaration patterns are exact. A lifted operator or conversion runs, and can fault, only when a value is present; Roslyn does not mark nullable conversions as checked, so the checked context is read from the syntax. `bool?` `&` and `|` are three-valued: `false & null` is `false` and `true | null` is `true`. Boxing yields `null` without a value and otherwise a fresh box, as boxing the value does. `Equals` against `null`, a boxed `T` or a boxed `T?` is exact, as is `GetHashCode` over `int`, `uint`, `bool` and enums over `int` or `uint`; `ToString` is `""` without a value and `"True"` or `"False"` for `bool`, and otherwise formats through the current culture, an unknown call. Reading `Value`, or converting to `T`, when there is no value builds an `InvalidOperationException` through runtime resources; that path is an unknown call that throws, so a read that may be empty is not proven pure or throw-free. `Equals` against another object, other hash codes, enum boxing, conversions into enums, user-defined conversions and lifted operators over other types are not modeled. Wrapping a value is an allocation the CLR does not make and is treated like building a struct value.

Objects have runtime types. An allocation of a class, delegate or array records its object's exact runtime type, and a box of a `bool`, an integer, an enum, a modeled readonly struct or a nullable value records the boxed value type and holds the value. `is T`, `as T`, type and declaration patterns, unboxing (with its `NullReferenceException` and `InvalidCastException`), reference downcasts and `Equals(object)` on scalars and nullables read that type. For each pair of a runtime type and a tested type the answer comes from the C# conversion rules, and pairs where the CLR is more permissive than C# (array covariance between same-size primitives, generic interfaces of arrays, unboxing between same-width primitives) stay unknown. An object whose allocation the analyzed code does not contain, such as a parameter, a field value or the result of an unknown call, has no known runtime type: a type test on it is neither true nor false in a proof, and a counterexample that depends on it is not replayable, so it is never refuted from a guessed type. A counterexample's entry object takes the runtime type the solver chose only when every declared type it is seen through admits that type. Open generic types, `as` to an array or string, and downcasts to arrays are not modeled. A matching latest store determines a later read. Calls or writes outside the precise store model may forget contents, leaving approximated values. An element write does not implicitly change a field. Exact instance-field value reasoning excludes fields declared on explicit-layout types, including readonly fields.

Approximation values can support sound over-approximate proof obligations only within the checks implemented by the worker. They cannot be treated as independently executable concrete counterexamples.

## Calls and loops

Source and admissible metadata calls are resolved through compiler evidence and lowered or modeled within the available boundary. A dispatched call whose body the program text fixes is lowered like a non-virtual one: a `base.` call, a sealed override or a member of a sealed type, and a call on a receiver whose static type is sealed, which runs the final override along that type's bases. Unknown targets and recursive or opaque call paths carry conservative effects and values. So does a source callee whose body does not lower, or whose expansion runs out of the lowering work budget or does not fit in what is left of it: the call runs as an unknown call that may do anything, throwing included, after its `Requires` is checked at the call as usual. A `new` of a source class through a declared constructor that the lowerer does not expand runs that constructor the same way, once the arguments have run and the object is allocated: a constructor of a class whose instance initializers cannot be run apart from its body, such as one of a generic class or of a class with a field-like event, and a class's primary constructor, which has no body to expand and no `Requires`; a primary constructor with attributes is not called. The object is then unknown to the caller, since the unknown call may have stored anything into it or published it. The class's type initializer, and every enclosing type's, must still be admitted, as for any call into the class. The work the abandoned expansion spent is given back, up to three more budgets in all for one verified body, so the rest of the body can still lower. The method being verified has no such fallback: when its own lowering runs out of work, its claims are `Unknown`. An external declaration is not a source-body proof. One exception: a call that recurses into the method being verified, an ordinary method without `Requires`, is assumed pure by the purity check alone, by induction on recursion depth. If the body is pure whenever its nested calls are, the first impure step of any execution would sit in a frame whose nested calls had all been pure, which the proof excludes. Every other check, and a recursive helper that is not the verified method, still treats such a call as unknown.

Natural loops use cut encodings and invariant candidates. Candidate invariants must pass establishment and preservation checks before use in a proof. Bounded witness search is separate from the proof encoding; finite unrolling cannot prove an arbitrary loop or termination. Unsupported CFG shapes or exhausted construction limits produce Unknown.

Call preconditions and body checkpoints are obligations, not unchecked assumptions. Each clause of a modeled call's `Requires`, including closed parameter attributes and companion clauses, is a `CallPrecondition` claim of the caller. The caller must establish the clause from its own entry domain on every path that reaches the call, so a caller with no `Requires` of its own must establish it for every input. A body that declares nothing is selected automatically when it makes a modeled call. A `Refuted` claim fails the build under every policy, and an `Unknown` one fails `require-proven`, except that a claim that ran out of time does not (see below). The callee's `Requires` is not assumed after the call. A call inside an inlined callee belongs to that callee when it is verified on its own, so one violation is reported once.

A modeled call is an invocation, construction or accessor call, from a body that lowers exactly, to one of:

- A non-virtual source callee in the same compilation with by-value parameters. Every clause of its `Requires` is checked. A generic callee runs its declaration. A parameter or result whose constructed type differs from the declared one is admitted when both types are references: a class, an interface, a delegate (a `Func<T, bool>` parameter receives a `Func<int, bool>`) or a type parameter, except `string` and `object`. The callee then sees the caller's reference unchanged. A type parameter instantiated with a scalar, `string`, `object`, a one-dimensional array or a struct other than `Nullable<T>` takes that type in the callee instead, so a parameter or result of that type parameter receives the caller's value; for a struct, `x is null` is `false` and `default(T)` of a modeled struct is its default. A call through a constraint on such a value is a dispatched call, which stays unknown, and on a mutable modeled struct is not modeled, since it may change the value. Other instantiations, such as `Nullable<T>`, stay unsupported. Invoking a delegate stays an unknown call.
- A callee in another assembly that is not dispatched (not virtual, abstract, an override or an interface member) and not generic, whose arguments are all by value and none is a `params` array. A non-lifted user-defined binary operator declared in another assembly is a call to its operator method with the two operands as arguments. Three kinds of clause are checked, in this order. A companion that the calling project declares for the callee with `[ContractFor]` contributes its `Requires`; its claims are marked as declared by the calling project. The callee's closed parameter attributes (`[NonNull]`, `[Positive]`, `[InRange]`) are read from the referenced image whose hash the compiler artifact records, so a reference assembly qualifies. When the callee's project is a project reference built in the same build, the `Requires` that project exported for the callee are checked too; see [contract exports](#contract-exports). A call's clauses are checked together or not at all.

A metadata clause has no source location. Its claim names the assembly, the member, the parameter and the attribute, as in `[InRange(0, 9)] on parameter 0 in Library`, and a violation is reported at the call. The attribute is the contract the referenced image declares. A different implementation loaded at run time is outside this model.

### Contract exports

A verified project writes a contract export for each target framework: `obj/<configuration>/<framework>/SharpProof/contracts-export.json`. It lists each public or internal method, constructor and accessor with a source `Contract.Requires`. Each entry holds the callee's documentation ID, its clauses as portable IR with their source locations, and a digest of the declaration and contract source. Closed attributes are not exported; they travel in the binary. A callable whose clauses read anything but its parameters, such as a field or `this`, is exported as incomplete, without clauses.

An MSBuild step inside each compilation stamps the export with the module version ID and SHA-256 of the reference and implementation assemblies that compilation produced. A compilation that does not complete the compiler capture (verification off, or the collector failed) removes the previous export instead. A referencing project passes the export of each project reference, for the framework it references, to its compiler as an additional file. It accepts the export only when the stamp names the exact image it resolved for that assembly, and the compiler artifact records the export's hash and stamp so the worker rejects a row that cites anything else.

An exported clause's claim cites the clause's file and line in the exporting project and names that project, as in `at Library.cs(4,9), exported by Library`, and a violation is reported at the call. The clause is an obligation of the caller; it is never assumed after the call.

Contract exports cover only:

- Project references built in the same build. A package, a plain assembly reference or a project built separately has no export.
- The framework the reference resolves to. Another framework's export is not consulted.
- Calls that are not dispatched.

A missing export, an export that cannot be read, or one whose stamp does not match is never checked. When the export can be read, its callees' calls are counted as unchecked. A call to an incomplete callable is counted as unchecked as well. The stamp binds the export to the reference image, which does not change when only a method body or a `Requires` changes. The export cannot go stale that way, because every compilation of the exporting project restamps or removes it.

Nothing else is checked. A passing build says nothing about these calls:

- Calls in a body that does not lower exactly or is abstracted. That includes a source callee that runs as an unknown call because it does not lower in its caller, or runs out of work there: its own calls are checked only where it is verified on its own.
- Calls in lambdas, and in local functions that a selected body does not inline. Lambdas and local functions are not selected as roots. A local function is inlined when it captures nothing, or when its owner calls it and it only reads the owner's locals and parameters; it then reads the owner's own variables.
- Calls in top-level statements, and in property accessors and operators unless a selected caller lowers them inline.
- Calls to virtual, interface and abstract callees. A `Requires` on an interface or base method is therefore not checked at its dispatched calls.
- Calls in async bodies, calls to async callees, calls to extern callees, and calls to callees with `ref`, `in` or `out` parameters, except the source calls described next. An awaited call to a source async method runs the callee's body, as [async methods](#async-methods) describes, but the async caller is not a root, so the call is still counted. A source callee's `ref` or `out` parameter is admitted when its argument is a local or parameter of the caller, no variable is passed by reference twice in the call, and the call is outside every `try` region of the caller. The callee then works on its own copy, which is written back to the variable when the call returns normally; an exception that leaves the caller ends the variable, so no handler can observe the difference. The caller's own `ref`, `out` or `in` parameter, when it is the caller's caller's storage, is not copied: the callee's parameter is the same reference, so each store the callee makes to it is a write to argument state, and any write forgets it, as in the caller's own body. A source callee's `in` parameter is admitted when its argument is a place nothing can write while the call runs: a value that is not a variable, which C# copies into a temporary; a local or by-value parameter of the caller that the call passes nowhere else by reference and does not call a struct member on; or a `readonly` field of a class or a `static readonly` field, outside constructors and `init` accessors. A local's value is read once the arguments have run, as for `ref`. Fields, array elements and ref locals passed by `ref`, `out` or `in` otherwise stay unmodeled: C# passes the place itself, which the callee could see change through another alias.
- Calls to a callee whose type, or an enclosing type, has a static initializer outside the admitted classes; [Effects](#effects) lists them. The exception is a callee declared in the caller's own type, which is inlined and checked. When that type's initializer is not effect-free, a call that satisfies the clause is still `Proven`, but a violation is reported as `Unknown` rather than `Refuted`, as the replay rule below requires.
- Calls in a body selected only for its calls, once the compiler artifact reaches 24 MiB. Such bodies are left out, last callable ID first, so the artifact stays under its 32 MiB limit. A body with a declared claim is never left out, so a project its declared claims alone push past the limit still fails with SP0049.
- Calls whose claim ran out of time, with reason `MethodTimeout` or `ProjectTimeout`. The claim reports `Unknown`, but it does not fail `require-proven`: its caller's SP0047 is a warning there, as under `warn-on-unknown`, because machine load alone must not decide a strict build. Any other `Unknown` reason still fails `require-proven`, and so does a declared claim that runs out of time, including one in the same caller.
- A `Contract.Requires` in another assembly's source without an accepted contract export. This is the main public-API case: `Contract.Requires` is compiled out of the library's binary, so a package's callers cannot see the clause, let alone check it. Only the library's closed parameter attributes, or a companion the calling project declares, are checked.
- Calls into another assembly that are dispatched or generic, or take a `ref`, `in`, `out` or `params` argument; calls whose attributes cannot be read from an authenticated image or paired with the symbol's; calls to a callee whose companion does not resolve cleanly; calls to a callee whose export is incomplete or whose exported clauses cannot be rebuilt over its parameters; and calls with an argument whose representation the verifier cannot convert to its parameter's.

The build summary, the tool report and SARIF report the number of source calls whose callee declares a precondition the compiler can see and that no claim checks. The manifest's `UncheckedCallSites` holds the part known at compile time, and the reports add the calls whose claims ran out of time. The count covers every case above except a `Contract.Requires` in another assembly's source with no readable contract export, which the compiler cannot see. It also counts calls in dead code. Zero therefore means no visible call was missed; it does not mean every precondition in the program was checked. The advisory SP0027 can still report a definite violation at an unchecked call; its silence is not proof.

General virtual dispatch, recursion, async execution beyond [async methods](#async-methods), and arbitrary metadata bodies are not blanket supported just because a related form can be lowered. See [coverage and limits](docs/coverage-and-limits.md).

The [language reference](docs/language-reference.md) distinguishes admitted operations, modeled call boundaries, and opaque or unsupported cases, with implementation and behavioral test references. A supported operator does not imply that every operand type, lifted form, or containing callable is admitted.

## Effects

Native effect claims are decided over the same Total program, through the exception and effect-site verifiers. They include `DoesNotThrow`, `AllowedExceptions`, `ZeroAllocations`, `EnforcePure`, `AllowedCapabilities`, and `EffectContract`.
Exception proofs also require positively admitted entry initialization. The compiler emits a native exception constraint only when the target type and source module initialization have no modeled synchronous fault. Empty initializers, built-in constants, simple static-field writes of admitted values, and the audited parameterless `System.Object` construction can satisfy this check. Bound conversions and initialization dependencies are checked; an initializer that calls unproved code, invokes a property setter or user conversion, or has an unproved dependency yields Unknown, unless it is a closed computation (see below), which never throws. An unused base or enclosing type is not an initialization dependency merely because of inheritance or nesting.

This exception check is separate from entry purity and allocation checks: a no-fault constant write to a mutable static is a write to static state, which the fresh-values class below admits only for claims that ignore allocation. Existing opaque source-callee boundaries remain conservative. A non-null receiver does not add the effects of constructing that receiver to its instance method. Ordinary allocation follows the existing modeled-exception policy; arbitrary initializer programs and precise initialization-exception summaries remain unsupported. Missing native exception constraints cannot supply a proof, and compiler artifact schema 31 rejects the older admission meaning.

Purity, allocation, capability and effect-contract claims also require entry initialization with no observable effect. The CLR runs a type initializer at a time the program does not control: before the first access to a static member, or, for a `beforefieldinit` type, at any earlier point. So the initializer of the callable's declaring type, and of every enclosing type, counts as part of entry. No code can see a type's statics before its initializer has run, except code the initializer itself reaches through a cycle. An initializer that only fills in the type's own statics, from values it makes itself, therefore changes nothing a body can observe. SharpProof admits two classes of such initializers:

- **Constants.** Static readonly fields and get-only static auto-properties are initialized from compile-time constants or default values. A target-typed `default` or `default!` produces the target's zero value, including for type parameters, and never calls a constructor. A static constructor may be empty or only store such values into those members. `string.Empty` and `Environment.NewLine` count as such constants: the runtime sets the first before any managed code runs, and the second returns a string literal of the platform build. This class runs no other code and allocates nothing, so every effect claim accepts it.
- **Fresh values.** As above, but a value may also be one of these:
  - a one-dimensional array of constant length up to 65,536, with admitted elements, or an array collection expression, including an empty one;
  - a boxed value, or a `decimal` constant, which the compiler builds with a `decimal` constructor or reads from `Decimal`'s own constants;
  - `Array.Empty<T>()`, which returns one cached zero-length array per `T` and runs no code of `T`;
  - `typeof(T)` of a type with no type parameters that always loads. It loads a type handle and returns the runtime type object that the runtime makes once per type; it runs no type initializer. C# accepts some types the runtime refuses with `TypeLoadException`, so every part of the type must be a core-library type or a source class, struct, interface or enum with no `StructLayout(LayoutKind.Explicit)`, `FieldOffset` or fixed buffer (an explicit layout can overlap a reference with other data), no struct that contains itself through its instance fields, and a class base that is neither sealed nor static. Its containing types, base types, interfaces, type arguments and value-type fields must load by the same rule, and a type argument must be given for an unconstrained parameter, or be a non-nullable value type for a `struct` one;
  - `StringComparer.Ordinal` or `StringComparer.OrdinalIgnoreCase`, `Type.EmptyTypes`, `Enumerable.Empty<T>()`, `new IdnMapping()` and `SearchValues.Create` over a constant string of at most 65,536 characters. Their framework code makes a comparer, an empty array or sequence, an object with an empty constructor and a character lookup object; it calls no user code, reads no culture or other ambient state and cannot throw. `SearchValues` picks its implementation from the characters and the hardware, never from state a program can change. Each of these members, `string.Empty`, `Environment.NewLine`, the framework collections and the `Math` functions of closed computations below is bound by identity: its type must be the one the compilation resolves for its full name, which is none when another reference declares the same name, and must come from a framework assembly. A referenced lookalike, even one named through an extern alias, stays an entry effect. Culture comparers, other `SearchValues` arguments and other framework objects stay entry effects;
  - a lambda, or a method group of a static method;
  - `new object()`;
  - a `new` of a framework `List<T>`, `Queue<T>`, `Stack<T>`, `Dictionary<TKey, TValue>`, `HashSet<T>`, `ConcurrentQueue<T>` or `ConcurrentDictionary<TKey, TValue>` through its parameterless constructor, a constant capacity from 0 to 65,536 (not for `ConcurrentDictionary`), or, for a string key, `StringComparer.Ordinal` or `StringComparer.OrdinalIgnoreCase` as the comparer of a `Dictionary`, `HashSet` or `ConcurrentDictionary`. A collection initializer may call `List<T>.Add` with admitted values, `HashSet<T>.Add`, and `Dictionary` `Add` or its indexer with admitted values. Every key a `HashSet` or `Dictionary` hashes must be a non-null constant `bool`, `char`, integer, string or enum, ASCII under `OrdinalIgnoreCase`, or, for a `Type` key, `typeof` of a type that always loads (see `typeof` above), which hashes and compares by identity in framework code; two operands naming one runtime type, such as `nint` and `IntPtr`, are the same key, and no `Dictionary.Add` may repeat a key under the comparer, since that throws. These constructors and `Add` methods only allocate and store: they call no member of the element or key type, since the framework picks a key type's default comparer itself, and cannot throw except by running out of memory. A comparer from source, `EqualityComparer<T>.Default` passed explicitly, a culture comparer (`CurrentCulture` reads the ambient culture, which may be a user subtype, and the invariant ones load culture data), other key types, other constructors and other initializer members stay entry effects. The collection is mutable, so a body's read of a static that holds it stays an ambient read;
  - a `new` of a source class, or of a source struct, explicit or target-typed, through a constructor that only stores its own parameters or admitted values into the new instance's own fields and auto-properties. The class or struct has no object initializer, no chained `this(...)` constructor and no `~T()` method, and its type initializer is itself admitted. A class whose base classes down to `object` are all declared in source, as ordinary classes without a destructor or a primary constructor, may chain with `: base(arguments)`, written or implicit, to a base constructor that meets the same rules; the arguments may read the derived constructor's parameters, and the base class's type initializer must be admitted too, unless it is the one being run. A base constructor's store into a virtual or overriding auto-property is not admitted, since the object's most derived class may override it. Such an object is not an immutable value for the cached-read rule below, which checks only the created class's own fields.
  - a store, by a field or auto-property initializer or by the static constructor, into the type's own mutable static field or static auto-property with a setter, other than a `[ThreadStatic]` one, even of a constant. No code reads such a static before the initializer finishes, so the store is no more observable than one into a readonly static; afterwards other code may store into it, so a body's read of it stays an ambient read. A `[ThreadStatic]` static starts zeroed on every thread but the one that ran the initializer, so a store into it stays an entry effect, as does a static field-like event;
  - a read of a readonly static field that is neither volatile nor `[ThreadStatic]`, or of a get-only static auto-property of a class or struct whose getter the compiler implements and is not `[MethodImpl(MethodImplOptions.Synchronized)]`, which would take a lock, of the type itself or of another source type whose own initializer is admitted. Such a field, or the property's readonly backing field, holds only what its initializer stored, so the read is not an ambient read, and it adds nothing beyond that initializer's class. A read of a mutable static or of a static property with a setter is an ambient read and stays an entry effect.

- **Closed computations.** An initializer that the two rules above do not admit is run at analysis time when it is a closed computation: its static field and property initializers, in declaration order, then its static constructor, reading nothing but constants, the readonly statics it is setting, the readonly statics of other source types whose initializers are themselves admitted, and the values it makes. It may call source methods and constructors that are neither virtual nor generic, including validating ones that only throw for other arguments, and run loops and branches. Integer arithmetic is exact, including checked overflow, division by zero and `MinValue / -1`. `BigInteger` arithmetic and the `BigInteger` conversions to `decimal`, `double` and `Int128` are run exactly; floating-point, `decimal` and 128-bit results can only be stored, so no branch depends on rounding. Floating-point `+`, `-`, `*`, `/` and `%`, unary `+` and `-`, conversions between `float` and `double`, unchecked conversions from them to integral types, and `Math.Ceiling`, `Floor`, `Truncate`, `Round`, `Abs` and `Sqrt` of a `double` never throw, so they run and yield such stored-only values, as in Humanizer's `ByteSize` bounds. A checked conversion to an integral type and any conversion to `decimal` can throw and give up. A call the compiler omits through `[Conditional]` does not run. Anything else gives up: a throw, an exception region, a library call, a virtual or interface call, generic code, boxing, string operations, a mutable static, an element of an array or a mutable field of an object another initializer made, a cycle, or more than 131,072 steps. When the run finishes, the initializer never throws, and it is deterministic, so running it again at any time changes nothing a body can observe. It belongs to the constants class when it allocated nothing, and to the fresh-values class when it made a class instance, an array or a `BigInteger`. NodaTime's `Duration`, `Instant`, `Offset` and `LocalTime` bounds are closed computations. A body that reads a readonly static, or a static get-only auto-property, of such a type sees the value the run left there, when that value is a `bool`, an integer, an enum, `null`, or a modeled struct made of those: the read runs the initializer, which then has finished, and nothing else can store into the static. A struct value is built as a fresh immutable object, as `new` builds one. The exception is a callable the initializer itself runs: a call from inside the initializer may see the static before it is set, so for such a callable the static stays an unknown value.

  The last two classes write no state a body can observe and cannot throw except by running out of memory; the fresh-values class otherwise calls no other code than the framework collection constructors, `Add` methods and framework values above. The lambda and method-group delegate caches the compiler generates are not observable state. Fresh values do allocate, and the first call that runs the initializer pays for that. So `EnforcePure` and `AllowedCapabilities` accept this class, while `ZeroAllocations`, `EffectContract` and resource bounds do not. Compiler artifact schema 61 records the distinction as `EntryConstructsFreshValues`.

A body may also read a readonly static that is neither volatile nor `[ThreadStatic]`, or a static get-only auto-property, when its type's initializer is admitted and its own initializer stores an immutable value. The static must have no other initializer or static constructor that stores into it or takes a writable reference to it. Admitted values include `null`, a constant string, a boxed constant (a `bool`, an integer, a `char`, a floating-point number or an enum), and `new object()`.

A private cache on a top-level source type may also hold an instance of a sealed, top-level source class with private readonly instance storage. Its constructor may only store constants, default values and copies of admitted by-value arguments into its own fields or get-only auto-properties. The static initializer may pass a deferred delegate, such as the one in NodaTime's `ParseResult<T>.ValueStringEmpty`. The class and the cache owner must pass source checks for by-reference access, receiver escapes and reflection. Allocation accounting still includes the initializer's work. Invoking a cached delegate is governed by the ordinary call rules.

The cache read produces an opaque reference and has no ambient read effect. The reference may be `null` because a callable reached from the initializer can observe it before assignment. Its identity and contents are unknown. Mutable objects such as arrays, and library-produced values such as `Task.CompletedTask` or `Task.FromResult`, remain outside this read rule.

Any other static field of a source type whose initializer, and every enclosing type's, belongs to one of the three classes above is read as in a type with no initializer. The read runs that initializer, which has no effect a body can observe. The value is unknown and the read is a read of static state, so `EnforcePure` stays `Unknown`. A volatile field, a field without independent storage, and a static of a type whose initializer is not admitted stay unsupported. When the initializer allocates, claims that count allocation report `CalleeTypeInitializer`, as for a call.

The same holds for a static auto-property, with or without a setter, and for a static getter whose whole body returns one static field of its own type with the property's type: a read runs the getter, which runs the type's initializer and then reads that field. The read is modeled as a read of the field under the rule above. Any other static getter of such a type is inlined as a call into the type.

A body may likewise store into, increment or compound-assign a mutable static field, or the backing field of a static auto-property, of a source class whose initializer, and every enclosing type's, belongs to one of the three classes above. The store runs that initializer first and then writes the static as in a type with no initializer. It is a write of static state, so `EnforcePure` is refuted for a plain store or a discarded `int` increment. Any other increment or compound assignment, in a type with or without an initializer, also reads the static's unknown value; replay does not reproduce that read, so `EnforcePure` stays `Unknown`. Every later read of the static is unknown as well, so no value the initializer or the body stored is assumed. Only a type's own initialization may store a readonly static, so the known and immutable values above are unaffected, and an initializer that stores a static a body can write leaves no known values. Volatile and `[ThreadStatic]` statics, statics of a struct, and statics of a type whose initializer is not admitted stay unsupported.

Everything else is an entry effect, and the claim stays `Unknown` with SP0047 `Advisory:EntryInitialization:TypeInitializer`. That covers any other call (including other collection initializers and metadata constructors), a read of a static of a metadata type or of a type whose initializer is not admitted, a throw, a cross-type cycle, a static constructor with control flow, locals or other statements, and a write to a mutable, volatile or `[ThreadStatic]` static or to a field-like event. A source callee in another type is inlined when that type's initializer, and every enclosing type's, belongs to one of the three classes above; a constant store into a mutable static is also admitted there, as before, but leaves the entry incomplete. Such an initializer can run in the middle of the body, and a nested type's member can run before its enclosing type's initializer has, but none of the three classes has an effect a body can observe or throws. When a callee's initializer belongs to the fresh-values class, or is a closed computation that allocates, claims that count allocation report `CalleeTypeInitializer`. A callee declared in the caller's own type needs no such check: its body runs under the initializer the caller already answers for, exactly as if it were written in the caller, so the entry rule above covers it. Constructed generic types are distinct types here. A module initializer is always an entry effect.

Constructing a source exception type whose constructor only passes its own parameters, in order, to a core exception constructor of its direct base (`Failure(string message) : base(message) { }`) allocates that type and runs that base constructor, with the base constructor's modeled effects; the type must declare nothing but such constructors. Any other source exception construction is an unknown call.

An iterator, a method whose own body contains `yield`, runs none of that body when it is called. The call creates the compiler's enumerator object, which holds the receiver and the arguments, and returns it. The body, argument checks included, runs only as the result is enumerated, through later calls on that object. Effect claims describe the call, so an iterator, verified on its own or inlined into a caller, is lowered as one fresh allocation that it returns, with no recorded runtime type. `EnforcePure` and `DoesNotThrow` can then be proved, and `ZeroAllocations` is refuted at that allocation. Enumerating the result is a call on an object of unknown type and stays unknown. An async iterator is excluded by the signature check; see [async methods](#async-methods). An iterator with `Requires`, `Ensures` or `Assume` clauses, or companion facts, is not lowered, because its clauses would describe the enumeration, and a call to an iterator with preconditions is not modeled.

### Async methods

An `async` method that returns `Task`, `Task<T>`, `ValueTask` or `ValueTask<T>` and uses that type's default builder is lowered. Calling it runs its body on the caller's thread up to the first `await` of an operation that has not completed. The rest of the body runs once that operation completes, possibly on another thread and after other code has run. A claim on such a method describes everything the call starts, including the part that runs later.

- **Effects.** The body is lowered as written, and `EnforcePure`, `AllowedCapabilities`, `EffectContract` and `ZeroAllocations` cover every effect of it, including those after a suspension. The call may allocate the returned task, the state machine box and the exception holder, or may return a cached completed task. That is a possible allocation where the body starts, so `ZeroAllocations` and an `EffectContract` that does not permit `Allocates` are never proved; either is refuted when the body itself allocates on a path that replays.
- **Exceptions.** An exception that leaves the body does not leave the call: the builder stores it in the returned task, which faults. A faulted task that nothing observes raises `TaskScheduler.UnobservedTaskException` when it is finalized, which runs whatever handlers the process registered. So an exception that can leave the body reaches an unknown call, and the other effect claims are proved only when no exception can leave it. `DoesNotThrow` and `AllowedExceptions` stay `Unknown` with `UnsupportedContract`: the call never throws synchronously, so the claim as stated would always hold and would say nothing about whether the task faults.
- **Contracts.** `Requires` and `Assume` are bound as for any method. `Ensures` and return-value attributes are not, and the claim stays `Unknown`: the result is the task's, available only when it completes, and a postcondition would describe that completion. Resource bounds stay `Unknown`, except on a [configured async join](docs/resource-bounds.md#configured-async-join-source-work).
- **Awaiting a source async call.** `await M(...)`, or `await M(...).ConfigureAwait(c)` with a constant `c`, where `M` is a source async method that is lowered here and the call is not dispatched or resolves to `M`'s body, runs `M`'s body in place. `M` runs on the caller's thread up to its own first suspension, and the caller's code after the await runs only once `M`'s task completes, so `M`'s whole body comes first. The await's value is `M`'s `return` value. An exception that leaves `M` faults its task, and the await rethrows that same exception object, so it reaches the caller's handlers as from a synchronous call. When `M` has an await of its own, it may have suspended. Then the caller resumes later, posted to the synchronization context it captured unless it configured the await not to, after any other code has run. So `M`'s body is followed by an unknown call that does not throw. If `M`'s body does not lower, or runs out of work, the call and its await are unknown calls.
- **Every other await** is an unknown call that receives the awaited value. It may do anything, throw any exception and produce any value. This covers awaiting a parameter, field or local, a metadata call such as `Stream.ReadAsync`, a dispatched or delegate call, `Task.CompletedTask`, `Task.FromResult(x)`, `Task.Yield()` and custom awaitables. Their awaiters can read an `IValueTaskSource`, post to a synchronization context or run arbitrary code, and while the body is suspended any other code may change any memory.
- **Not lowered.** `async void`, whose exceptions are rethrown on the synchronization context; async iterators; methods with an `[AsyncMethodBuilder]` attribute and other task-like return types, whose builders run their own code; async instance methods of a struct, which run on the state machine's copy of `this`, so a store to `this` is not a store to the caller's value; and bodies with `await foreach` or `await using`. A call to an async method that is not the operand of an `await`, such as one stored, returned, passed on, or read through `.Result` or `.Wait()`, is not modeled, from a synchronous or an async body. Neither is the body of an async lambda or an async local function, other than an awaited call to the latter.
- **Calls.** Calls inside an async body are not call-precondition roots, so a `Requires` they violate is counted as unchecked, as for lambdas.

The model leaves out the runtime's own diagnostics, as it does elsewhere: an in-process `EventListener` enabled for the task event source, or a debugger tracking async causality, observes builder events, and the restored `ExecutionContext` notifies `AsyncLocal` change handlers only when the body changed an `AsyncLocal`, which takes an unknown call.

Converting a lambda or anonymous method to a delegate type runs none of its body; the body runs only when the delegate is invoked, and invoking a delegate is an unknown call. A lambda that captures a local, a parameter or `this` gets a new delegate on every evaluation, lowered as a fresh allocation of the delegate type, so `ZeroAllocations` is refuted when one is reached. A lambda that captures nothing reads a delegate the compiler caches in a static field, which only its first evaluation allocates; that cache is not observable state. Its creation is a possible allocation and its value an unknown reference. A capturing lambda whose value an optimized build may discard, being stored only into a local nothing reads, is treated the same way. The compiler allocates a closure frame where the scope of a captured local or parameter begins, whether or not the lambda is then reached, so a body with a lambda that captures one of its own variables begins with a possible allocation. Allocation claims stay `Unknown` for both. A captured variable is shared between the method and the delegate, and an unknown call that received the delegate may invoke it while the method runs. So a lambda is lowered only when no anonymous or local function in its declaring method writes, takes a reference to, passes by `ref` or `out`, or calls a member that may mutate a struct value through, a variable the lambda captures from that method; the method's own writes are allowed, since they change only what a later invocation reads. Not lowered either are a lambda converted to an expression tree, which runs library code; one that calls or declares a local function, whose captures compiler data flow does not attribute to the lambda; one nested in another lambda or a local function; and one that captures the receiver of a constructor, which would publish the object under construction. [Root parameter closures](docs/resource-bounds.md#root-parameter-closures) keep their separate frame model for resource bounds; other lambdas leave resource bounds `Unknown`.

An audited framework exception constructor given a non-null message only stores it. One that has to find its own message, such as `new ArgumentNullException(nameof(x))` or the stub bodies `throw new NotSupportedException();` and `throw new NotImplementedException();`, looks it up in runtime resources, which enters a runtime lock and can run ambient culture callbacks. An effect claim on a method that reaches such a construction is therefore `Refuted` when the lock replays and `Unknown` otherwise. The constructors whose lookup is modeled this way, and the `SharpProofTrustExceptionMessages` opt-in that assumes the lookup has no effects, are listed in [configuration](docs/configuration.md#trusting-exception-messages); any other framework exception construction that looks up a message is an unknown call.

Effects distinguish receiver, argument, captured, static, and ambient reads/writes; allocation; exceptions; synchronization; nondeterminism; native code; and reflection. Capability flags are a separate closed set. Each flag is independent: permitting `Throws` does not permit `Allocates`.

Observable purity excludes modeled externally observable effects and relevant ambient reads. A local operation is not automatically externally observable; classification depends on the modeled region and escape behavior. Calls with incomplete information retain conservative may-effects.

An interpolated string converted to `string`, whose holes have no alignment or format clause, is modeled when each hole is a `string`, `char`, `bool`, built-in integer (`sbyte` through `ulong`) or reference of a class, interface, array or delegate type. A constant one is its literal. When every hole is a `string`, the compiler emits `String.Concat` over the parts, so it is lowered exactly as the equivalent `+` chain: the same content, null as empty, allocation and maximum-length rules, and four operands at most after constant coalescing. Otherwise the holes are evaluated in order and the result is a non-null string whose content is unknown. A `char` or `bool` hole formats with no culture and no user code. An integer hole formats through the ambient culture: a call that reads ambient state, so `EnforcePure` stays `Unknown`, and that, by the assumption below, cannot throw. A reference hole calls the value's `ToString`, which can be user code, so it is an unknown call. A result that always has a character (literal text, or a `char`, `bool` or integer hole) is a new string, so `ZeroAllocations` is not proved; the formatting handler's `ArrayPool<char>.Shared` buffer is not modeled state, since every renter already sees unspecified contents. A result that may exceed the runtime's maximum string length may throw, as for concatenation; a reference hole has no length bound, so it always may. Other hole types (enums, floating point, `decimal`, other structs, `Nullable<T>`, type parameters), alignment and format clauses, interpolated strings converted to `FormattableString`, `IFormattable` or a handler type, and an interpolated string that is an operand of `+` or `+=` stay unsupported.

`typeof(X)` loads the runtime's `Type` object for `X`. It has no effect, cannot throw, allocates nothing and does not run `X`'s type initializer, for a type parameter `T` as for a named type. The object itself is not modeled: the value is an unknown reference, which may equal any reference the program already holds and is not known to be non-null, so `typeof(A) == typeof(A)` and `typeof(A) != null` are not proved. Calls on it, such as `.Name` or `GetMethod`, are calls like any other.

Assumption: the ambient culture has no user-defined callbacks. When the CLR itself raises a fault, such as an out-of-range string or array index or an integer division by zero, it builds the exception message through a resource lookup that reads the ambient `CultureInfo`. A user-defined culture subtype can therefore run code at that point, as [ExceptionalFrameworkCultureTests](src/SharpProof.Specs.Tests/ExceptionalFrameworkCultureTests.cs) records. The verifier treats these runtime faults as callback-free, so a program that installs such a culture is outside this model. The same assumption covers an integer hole of an interpolated string, which formats through the current culture's `NumberFormatInfo`: it runs no user code, cannot throw, and yields at most 64 characters, so a culture whose negative sign is longer is outside this model too. Faults behind cataloged calls, currently `Math.Abs(int)` and `Nullable<T>.Value`, stay conservative; see the [API specification catalog](docs/api-spec-catalog.md).

A body proof carries `CompleteMayEffectSummary`. A trusted external declaration carries `TrustedCompleteBoundary`, and remains an assumption. A replayed violation carries `DefiniteViolation` with a source site. A contradictory entry carries `VacuousEntry`. These certainties must agree with outcome, reason, witness, and vacuity; protocol validation rejects inconsistent tuples.

## Counterexample replay

Replay validates a candidate against the owned program, entry values, path, and claim. Solver-chosen values for unconstrained results or approximated reads are not arbitrary executable inputs. Undefined postconditions, unsupported replay operations, and missing source-site evidence cannot produce a definite refutation.

Heap witness decoding also checks the closed compiler type evidence. Distinct non-null references from incompatible sealed runtime types cannot be assigned one object token. Impossible aliases downgrade a candidate to Unknown; this witness filter adds no SMT premise. Compatible aliases and null remain allowed. Unused observations can still make a witness conservatively unreplayable, and reference-valued array accesses remain a current admission limit.

A call-precondition refutation is a concrete entry that reaches the call with the clause false and with no approximated value. Replay starts after entry initialization, so a type or module initializer that is not proved free of observable effects leaves the claim Unknown.

Effect witnesses identify the violating allocation, throw, write, or synchronization site. An inlined metadata site without a source position is insufficient for an emitted definite violation.

## Resources, caching, and failure

Native queries and methods have deterministic resource limits as well as wall-clock limits. Cancellation is cooperative within the worker and enforced by the launcher boundary. Completed solver work remains charged even when cancellation arrives later.

A response cache binds compiler artifact bytes, worker and specification identity, protocol, manifest, and budgets. Only validated complete eligible responses are reused. Stable semantic Unknown results may be cached; transient failures are excluded. Corruption or unavailable cache storage becomes a miss, never a changed semantic verdict.

Protocol validation and atomic publication are infrastructure boundaries. A malformed request, unowned output, or backend failure is a run failure or typed abstention, not an empty successful proof set. See [Unknown reasons](docs/unknown-reasons.md), [SMT lifecycle](docs/smt-lifecycle.md), and [preview support](docs/preview-support.md).
