# SharpProof.Dataflow reduction review

Scope: `SharpProof.Dataflow` and `SharpProof.Dataflow.Test`. This is a review only; no production or test source was changed.

## Baseline

| Area | Files | Lines |
|---|---:|---:|
| Production | 12 C# files | 1,188 |
| Tests | 9 C# files | 1,756 |
| Total | 21 C# files | 2,944 |

Line counts are physical lines from the current worktree and include blank lines/comments. The two `packages.lock.json` files are excluded.

## Recommended reductions

### 1. Reuse the shared domain-law helpers in generated tests (high confidence)

`SharpProof.Dataflow.Test/DomainLawAssertions.cs` already centralizes order/join, monotonicity, and havoc checks (roughly lines 5-164). The three sections in `GeneratedDomainPropertyTests.cs` repeat the same nested assertions for interval, sequence-cardinality, and nullness values (roughly lines 348-518). The hand-written domain tests also call the shared helpers, so the generated tests can be reduced to value generation plus three short calls per domain.

Suggested shape:

```csharp
DomainLawAssertions.AssertOrderAndJoinLaws(domain, Values);
DomainLawAssertions.AssertMonotone(domain, Values, transfer);
DomainLawAssertions.AssertConservativeHavoc(domain, Values);
```

Keep the generated value sets and any domain-specific widening-chain assertions. Do not remove the fixed random seed or the explicit non-empty assertions unless the helper is extended to retain them. Estimated reduction: 120-180 lines, with no loss of semantic coverage if the helper calls replace equivalent assertions.

### 2. Extract a test graph factory for `ForwardDataflowAnalysisTests` and `FiniteCfgConcreteOracleTests` (medium confidence)

Both files repeatedly construct `DataflowGraph<T>` instances, blocks, edges, and identity transfers. A small test-only factory for linear graphs, branching graphs, loops, and unreachable blocks would remove ceremony and make the scenario differences more visible. Keep factory methods typed and accept the transfer delegates/edge lists as parameters; avoid a universal object-based builder.

Preserve exact block IDs and edge ordering because graph validation, reachability, cyclic-block detection, and deterministic worklist behavior are tested. Estimated reduction: 50-100 lines.

### 3. Parameterize repeated domain-specific tests (medium confidence)

`IntervalDomainTests.cs`, `SequenceCardinalityDomainTests.cs`, and `NullnessDomainTests.cs` each contain similarly named tests for lattice laws, monotonicity, widening, and havoc. The shared assertion helpers already cover most of the common body. Replace only genuinely identical bodies with parameterized cases; retain domain-specific tests for canonicalization, endpoint behavior, arithmetic overflow, cardinality semantics, and invalid enum values.

This is lower priority than item 1 because NUnit parameterization can make failures less local and may require adapters for different value types. Estimated reduction: 30-70 lines.

### 4. Combine `DataflowGraph` adjacency construction (low-to-medium confidence)

`DataflowGraph.cs` creates and freezes predecessor and successor arrays separately (`CreateAdjacency`/`Freeze`, around lines 80-88 and 144-163). A single helper returning both frozen arrays, or a local adjacency record populated in one edge pass, can remove duplicated setup and improve locality. This is primarily a structural reduction, estimated at 8-20 lines.

Do not replace the sorted immutable adjacency contract: `Freeze` currently sorts neighbors, and callers/tests rely on deterministic traversal. Keep duplicate-edge elimination and all block-ID validation unchanged.

### 5. Simplify trivial facade methods only if API readability is not a goal (low confidence)

`ClosedAbstractDomain.Merge` is a one-line alias for `Join`, and `IntervalDomain.AddConstant` delegates directly to `Add`. Expression-bodied members could save a few lines, but these methods are part of the public API and their named facades improve discoverability. Treat this as optional style cleanup, not a meaningful reduction. Preserve public signatures and XML/API expectations.

## Do not reduce

- `ArgumentNullGuardBoundaryTests.cs`: the repeated lambdas deliberately verify every parameter name and call boundary. Consolidating them risks losing parameter-order coverage.
- `ForwardDataflowAnalysis.cs` monotonicity, widening-upper-bound, permutation-validation, and convergence-limit checks: these are executable safety contracts, not incidental verbosity.
- `IntervalDomain.Create` and `DataflowGraph.FindCyclicBlocks`: their branches encode endpoint, congruence, overflow, SCC, and self-loop corner cases. Refactor only with characterization tests and the existing generated/property tests still enabled.
- `FiniteCfgConcreteOracleTests.cs` oracle implementation: although long, it is an independent concrete reference and should not share production-domain logic.

## Verification plan for an implementation

1. Apply item 1 alone and run the Dataflow test project.
2. Compare test case counts and ensure generated interval, sequence-cardinality, and nullness tests still execute.
3. Apply fixture extraction separately, then rerun the targeted forward-analysis and concrete-oracle tests.
4. Run the repository-prescribed container command for the full Dataflow test target before accepting any line-count reduction.

The safest first change is item 1; it has the clearest one-to-one replacement with an existing shared helper and the largest likely reduction.
